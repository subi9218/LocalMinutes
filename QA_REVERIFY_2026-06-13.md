### [HIGH] I1 — Stale/unresolvable security-scoped bookmark routes an existing user to StorageSetupScreen; picking a different folder orphans all prior data
- **위치**: `lib/main.dart:45`
- **내용**: On the sandboxed App Store build, an existing user whose stored bookmark no longer resolves (folder renamed/moved/deleted, external or network volume unmounted at launch, or OS-invalidated scope) gets storageRestored=false, so storageReady=hasStoragePath&&storageRestored=false. IsarService.init() is therefore skipped (_isar/_directoryPath stay null) and the app shows _buildStorageScreen() even though the user already has data. In StorageSetupScreen._pickFolder, because IsarService.instance.isOpen is false, it calls IsarService.init() (NOT relocate). init() opens a brand-new empty DB at <newFolder>/Local Minutes Data and _migrateLegacyContainerDataIfNeeded only inspects the app container, never the old user folder. saveRecordingsFolderSelection already overwrote recordingsSavePath with the new path, so the app has no record of where the old data lived. Net effect: an existing user is presented an empty app and all prior meetings are orphaned (data files survive on disk but are unreferenced and the pointer is gone). Recovery requires the user to re-pick the exact original path. Native side confirms a stale bookmark that fails to resolve returns FlutterError->PlatformException->false, and even a resolvable-but-stale bookmark is never re-created (Dart ignores the returned 'stale' flag).
- **근거**:
```
final storageReady = hasStoragePath && storageRestored; ... if (storageReady) { await IsarService.instance.init(); }  // skipped when bookmark stale
// storage_setup_screen.dart: if (IsarService.instance.isOpen) { relocate(); } else { await IsarService.instance.init(); }  // opens EMPTY db at new folder
// security_scoped_bookmark_service.dart: try { return await startAccessingBookmark(bookmark); } on PlatformException { return false; }
```
- **수정안**: When hasStoragePath is true but the bookmark fails to restore at launch, do NOT silently fall through to StorageSetupScreen's folder picker as a fresh setup. Distinguish 're-grant access to existing folder <path>' (re-pick the SAME path, then relocate/open in place) from 'choose a new folder', and warn before opening an empty DB at a different folder. Also persist/keep the previous recordingsSavePath so init() can migrate from it instead of starting empty, and consider regenerating the bookmark when the native layer reports stale=true.

### [HIGH] I4 — Relocate into a folder that already contains a Local Minutes Data DB merges via putAll, overwriting colliding ids and scrambling meeting/transcript links
- **위치**: `lib/core/services/isar_service.dart:119`
- **내용**: Unlike _migrateLegacyContainerDataIfNeeded (which guards with 'if (await _hasIsarFiles(targetPath)) { delete legacy; return; }' at line 156), relocateToUserSelectedDirectory has NO target-has-data guard. It opens the target (which, if it already contains a Local Minutes Data DB, loads that existing data) and unconditionally putAll's the source rows when the source has data. Isar 3 put/putAll upsert by the object's existing Id, so any id overlap overwrites the target's row. Because both DBs assign ids from Isar.autoIncrement starting at 1, collisions are pervasive: source Meeting id=N overwrites target Meeting id=N, and independently source Transcript id=M overwrites target Transcript id=M even though that transcript's meetingId pointed at a different target meeting. Result: silent loss of the destination folder's existing meetings and corrupted meeting<->transcript links. Reachable when a user points the app at a synced/shared folder (iCloud/Dropbox across two Macs) or a backup that already holds a Local Minutes Data DB while their current DB also has data.
- **근거**:
```
if (hasData) { await next.writeTxn(() async { await next.meetingGroups.putAll(groups); await next.meetings.putAll(meetings); await next.transcripts.putAll(transcripts); ... }); }  // no _hasIsarFiles(targetPath) guard, unlike _migrateLegacyContainerDataIfNeeded
// repo: Future<int> saveMeeting(Meeting m) => _db.writeTxn(() => _db.meetings.put(m));  // put upserts by id
```
- **수정안**: Before merging in relocate, detect a non-empty target DB (mirror the _hasIsarFiles(targetPath) check) and either refuse with a clear warning, or re-key the incoming rows with fresh ids and remap Transcript.meetingId/groupId accordingly instead of blind putAll.

### [MEDIUM] D1 — No read/stall timeout: stalled mid-download stream never self-aborts
- **위치**: `lib/core/services/model_download_service.dart:182`
- **내용**: download() configures only connectionTimeout (TCP/TLS handshake) and idleTimeout. Per the Dart SDK, HttpClient.idleTimeout is 'the idle timeout of non-active persistent (keep-alive) connections' — it governs sockets sitting idle in the connection pool BETWEEN requests, not an active HttpClientResponse stream that is mid-body. There is no read/data-stall watchdog: `lastTick` (line 145) is used only to throttle progress callbacks, not to abort. If a server completes the handshake, returns 200 + Content-Length, then stalls mid-body, the response stream emits neither onDone nor onError, so `await completer.future` (line 182) blocks indefinitely. The progress bar freezes at its last value with status still 'downloading' and no error is ever surfaced automatically. Reachable on any flaky network (WiFi drop / hotspot) during a multi-GB model download. Impact is bounded: the bulk hero card and per-model card both render a working Cancel button (setup_screen lines 784-787, 1447-1460) that resets the UI, so the user is not PERMANENTLY stuck — but the download never self-heals, never times out, and never shows a network error on its own; recovery depends on the user noticing the frozen bar and manually cancelling/retrying.
- **근거**:
```
final client = HttpClient()
      ..connectionTimeout = const Duration(seconds: 30)
      ..idleTimeout = const Duration(seconds: 60);
...
      await completer.future;   // <- no stall/read timeout; hangs if stream stalls mid-body
// SDK: HttpClient.idleTimeout = 'idle timeout of non-active persistent (keep-alive) connections'
```
- **수정안**: Wrap the stream consumption in a stall watchdog: either `await completer.future.timeout(stallTimeout)` reset on each chunk, or a periodic Timer comparing `lastTick`/`received` and calling completer.completeError(networkError) + _subscription.cancel() when no bytes arrive for N seconds. Surface it as ModelDownloadException.networkError so the existing error UI/Retry path fires automatically.

### [MEDIUM] D4 — Zip extraction runs synchronously on the main isolate -> UI freeze for ~1.2 GB Core ML pack
- **위치**: `lib/core/services/model_download_service.dart:291`

No data loss; the freeze self-resolves when extraction completes.
- **근거**:
```

      await extractFileToDisk(destZipPath, extractDir);   // synchronous on main isolate, no compute()
// archive: writeContent->decompress() is sync; OutputFileStream uses sync FileHandle (1MB buffer)
```
- **수정안**: Offload extraction to a background isolate, e.g. `await Isolate.run(() => extractFileToDisk(destZipPath, extractDir))` (or compute()), and optionally drive the progress callback during extraction so the UI shows an 'Extracting...' state instead of a frozen download bar.
